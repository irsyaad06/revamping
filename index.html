Arsitektur yang disarankan

LapisanRekomendasi GBKRekomendasi JCC
Website publikSvelteKit + TypeScript. SSR atau prerender sesuai jenis halaman, cache CDN untuk konten publik.SvelteKit + TypeScript bila tim mengelola kedua situs. Prerender halaman stabil, gunakan SSR bila perlu.
API & CMSLaravel + Filament sebagai kandidat utama. Evaluasi Octane setelah uji beban. REST versioned untuk GBK.ID dan LOVE GBK, editorial ID/EN, preview, role, audit log.Laravel + Filament bila berbagi kompetensi tim. CMS untuk ruang, denah, agenda, portofolio, dan penerusan inquiry.
Data & layananPostgreSQL, object storage, Redis + Horizon untuk antrean dan cache bila dibutuhkan. Evaluasi Meilisearch via Scout jika pencarian bawaan kurang memadai. CDN/WAF, analitik, alerting, backup dan uji pemulihan.PostgreSQL, object storage untuk media/denah, CDN/WAF. Integrasikan email atau CRM sesuai proses sales.
Alternatif GBKSvelteKit + Hono/Node.js + admin SvelteKit, PostgreSQL, Redis/BullMQ. Pertimbangkan jika tim memilih TypeScript end-to-end dan sanggup membangun CMS bespoke.Tetapkan keputusan JCC dari workflow tim JCC. Dua PDF arsitektur membahas GBK.

Keputusan awal. Untuk GBK, pilih SvelteKit + Laravel sebagai kandidat awal bila prioritasnya meluncurkan CMS dan workflow editorial lebih cepat serta tim siap mengoperasikan PHP. Paket Hono menarik jika standardisasi TypeScript lebih penting dan waktu untuk admin kustom tersedia. Keputusan final menunggu uji CMS, prototipe Content API, dan uji beban Hono pada skenario yang setara. Benchmark dokumen bersifat internal dan Hono belum diuji di tabel perbandingan.

Alur GBK. Editor memublikasikan konten di CMS → Content API menyajikan data yang sama ke web dan LOVE GBK → job menginvalidasi URL CDN yang terdampak. Reservasi dan akun memakai otorisasi serta kebijakan cache terpisah dari konten publik.

Operasional. Pisahkan staging dan produksi. Tetapkan role editorial dan audit log, pengamanan admin, pembatasan permintaan, pengelolaan secret, retensi inquiry, serta pemantauan error dan backup. Konfirmasi pemilik sistem, SLA, dan lingkungan hosting sebelum menetapkan vendor cloud.

Prioritas rilis

P1

Rilis awal

GBK: navigasi, katalog, agenda, detail akses, tautan reservasi. JCC: katalog ruang, kapasitas, detail/denah, inquiry, agenda dan akses. Keduanya: CMS minimum, migrasi URL dan pengukuran.

P2

Pengembangan berikutnya

GBK: peta interaktif dan integrasi reservasi per venue. JCC: bandingkan ruang, tur virtual per ruang, routing CRM, dan portofolio.

P3

Setelah validasi proses

GBK: mesin booking sendiri hanya jika ada gap yang disepakati. Perlu inventori slot, biaya, konflik reservasi, status, dan pembatalan. JCC: portal penyelenggara bila dibutuhkan.

Kriteria penerimaan

AreaKriteria penerimaan yang diusulkan

PerformaTarget produksi p75 mobile LCP ≤ 2,5 s, INP ≤ 200 ms, CLS ≤ 0,1. Ukur baseline, uji beban cache hit/miss dan publikasi saat lonjakan trafik.
Metrik produkGBK: keberhasilan pencarian venue dan klik ke reservasi/peta. JCC: pembukaan denah dan inquiry valid per kunjungan halaman ruang. Tetapkan baseline sebelum menentukan target uplift.

  • Sepakati sumber kapasitas dan denah resmi JCC, penerima inquiry, waktu respons, dan integrasi CRM.
  • Tetapkan brand guideline, persetujuan foto resmi, inventaris redirect, dan target rilis setelah baseline.
